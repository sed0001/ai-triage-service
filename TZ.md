# ТЗ: ИИ-сервис первичной обработки обращений (MVP)

Проект для практики **VPk04.1 Учебный проект** (Кейс-лаборатория, Карьерный блок 2).

## 1. Проблема

Менеджеры поддержки тратят время на первичную сортировку обращений и типовые ответы,
из-за чего падает скорость реакции и качество обслуживания.

## 2. Решение

Сервис с языковой моделью: принимает текст обращения, классифицирует его по типу,
формирует черновик ответа, оценивает уверенность и решает, передать ли обращение человеку.
Все запросы и результаты сохраняются в БД (аудит) и логируются.

## 3. Контракт API

### POST `/triage`

Вход (JSON):

```json
{
  "text": "Здравствуйте, мне дважды списали деньги!",
  "channel": "email",
  "client_id": "client-001"
}
```

| Поле | Тип | Ограничения |
|---|---|---|
| `text` | string | 1…2000 символов, обязательно |
| `channel` | string | `email` \| `form` \| `chat` |
| `client_id` | string | 1…128 символов, обязательно |

Выход (JSON):

```json
{
  "category": "billing",
  "draft_reply": "Здравствуйте! Проверим двойное списание...",
  "confidence": "medium",
  "escalate": true
}
```

- `category`: `billing` | `support` | `complaint` | `other`
- `draft_reply`: 1–6 предложений (на русском)
- `confidence`: `high` | `medium` | `low`
- `escalate`: boolean — человеку, если низкая уверенность, конфликт или сбой

### GET `/health`

Проверка состояния сервиса и доступности БД. `200` — всё ок, `503` — БД недоступна.

## 4. Коды ошибок

| Код | Ситуация | Сообщение |
|---|---|---|
| 422 | Невалидный вход (нет/пуст/слишком длинный `text`, неверный `channel`, пустой `client_id`) | Список полей с причинами |
| 429 | Превышен лимит запросов для `client_id` | «Слишком много запросов…» |
| 500 | Ошибка записи в БД / непредвиденная ошибка | Понятное сообщение без деталей стека |

Сбой самой LLM — **не** ошибка API: возвращается `200` с `escalate=true` и шаблонным
ответом «передано оператору» (сценарий «если всё сломалось»).

Если `LLM_API_KEY` не задан, работает **демо-режим базы знаний**: готовые ответы
подбираются из `examples/knowledge_base.json` (точное совпадение → ключевые слова →
общий шаблон), чтобы прогнать демо можно было без ключа и без сети.

## 5. Надёжность и безопасность

- Валидация входа (Pydantic/FastAPI + отсечение пробелов).
- Секреты только в переменных окружения (`.env`, не в коде, файл `.env` в `.gitignore`).
- Лимитирование: скользящее окно N запросов/мин на `client_id` (по умолчанию `RATE_LIMIT_PER_MINUTE=5`).
- Фолбэк: при ошибке LLM/невалидном JSON → `escalate=true`, `draft_reply` = шаблон.
- Демо-режим без ключа: база знаний `examples/knowledge_base.json` (подбор по точному
  совпадению/ключевым словам), каждый ответ — `category`, `confidence`, `escalate`, `draft_reply`.
- Правило эскалации: `escalate=true`, если `confidence=low` или модель так решила.
- Системный промпт запрещает выдумывать факты и отвечать при нехватке данных.
- `temperature=0.2` для аккуратной классификации.

## 6. Аудит и логирование

- **SQLite** `data/tickets.db`, таблицы:
  - `tickets`: `id, created_at, client_id, channel, text, category, confidence, escalate, draft_reply, error`;
  - `channels` — справочник каналов (`email`, `form`, `chat`).
  Целостность: `channel` — внешний ключ на `channels`, `NOT NULL` и `CHECK` на обязательные
  поля и допустимые значения категории/уверенности/`escalate`; индексы по `created_at`, `client_id`.
- **Логи** в папке `logs/`:
  - `app.log` — все события сервиса;
  - `error.log` — только ошибки;
  - `requests.log` — аудит HTTP-запросов (метод, путь, статус, время).
- Отдельный файл логов/БД не содержит ключей.

## 7. Стек

- Python 3.10+, **FastAPI** (Uvicorn), Pydantic 2
- **SQLite** (встроенный модуль)
- **OpenAI SDK** → OpenAI-совместимый эндпоинт ProxyAPI (`https://api.proxyapi.ru/openai/v1`), модель `gpt-4o-mini`
- Опционально: Dockerfile

## 8. Структура модулей

```
app/
  main.py             # точка входа: lifespan, middleware, обработчики ошибок
  config.py           # настройки из env
  schemas.py          # контракт входа/выхода /triage
  logging_setup.py    # конфигурация логирования (logs/*.log)
  api/routes.py       # эндпоинты POST /triage, GET /health
  core/state.py       # синглтоны (лимитер, LLM-клиент, база знаний)
  core/rate_limiter.py# скользящее окно на client_id
  core/llm.py         # вызов LLM + разбор JSON + LLMError
  core/prompts.py     # системный промпт
  core/knowledge_base.py # подбор готового ответа без LLM (демо-режим)
  core/triage_service.py # оркестрация: лимит → LLM/БЗ → запись в БД
  db/database.py      # SQLite: инициализация, запись тикета, healthcheck
  examples/knowledge_base.json # готовые ответы для демо без ключа
scripts/demo_client.py  # демо-клиент с примерами обращений
tests/                 # pytest: валидация, лимитер, разбор JSON, база знаний
```

## 9. Критерии «готово»

- [ ] `POST /triage` отвечает по контракту, поля корректны
- [ ] История сохраняется в `tickets` (вход + результат + `error`)
- [ ] 422/429/500 возвращаются с понятными сообщениями
- [ ] Ключ LLM только через env
- [ ] Сценарий «всё сломалось» работает (фолбэк + эскалация): сбой LLM и отсутствие
      совпадения в демо-режиме возвращают шаблон «передано оператору»
- [ ] Демо-режим без ключа: тестовые обращения из `examples/test_data.md`
      воспроизводятся по базе знаний `examples/knowledge_base.json`
- [ ] Лимитирование 5 запросов/мин на `client_id`
- [ ] Логи в `logs/` (app / error / requests)
- [ ] README позволяет воспроизвести запуск за 5–10 минут
