# Отчёт по практике

**Кейс:** ИИ-сервис первичной обработки обращений (языковая модель + программный интерфейс + журналирование)

**Курс:** Профессия вайб-кодер · Карьерный блок 2 · Урок VPk04.1 «Учебный проект»

**Проект:** [`ai-triage-service/`](README.md)

---

## 1. Кому и какую проблему решаем

**Заказчик (симуляция):** онлайн-сервис (интернет-магазин / образовательный проект).

**Проблема:** менеджеры тратят время на первичную сортировку обращений и ответы на типовые запросы.
Из-за этого падает скорость реакции и качество обслуживания — сообщения приходят параллельно
из трёх каналов (email, форма на сайте, чат) и тонут в общем потоке.

**Решение:** сервис `POST /triage`, который автоматически:
1. классифицирует обращение (`billing | support | complaint | other`);
2. выдаёт черновик ответа для менеджера (`draft_reply`);
3. фиксирует историю обработки в базе данных (аудит);
4. эскалирует сложные/неоднозначные случаи человеку (`escalate`).

## 2. Ограничения и допущения

- Один основной эндпоинт: `POST /triage` (+ `GET /health` для проверки живости);
- максимум **4 категории** (`billing`, `support`, `complaint`, `other`);
- `text` — 1…2000 символов, обязателен, пробелы по краям отсекаются;
- `channel` — только метка источника: `email | form | chat` (реальные интеграции не подключаем);
- `client_id` — 1…128 символов, обязателен;
- лимит: **не более 5 запросов/минуту на client_id** (`RATE_LIMIT_PER_MINUTE`);
- секреты — только через переменные окружения (`.env`), в код не попадают;
- без RAG/полноценной базы знаний (это план v2);
- черновик ответа — **1–6 предложений на русском**, от лица службы поддержки, по строгому системному промпту.

## 3. Архитектура (схема блоками)

```
 Обращение (JSON)
      │ POST /triage
      ▼
┌─────────────┐   ┌────────────────────────────┐
│ Валидация   │──▶│ Лимитер (скользящее окно)  │
│ (Pydantic)  │   │ 5 req/min на client_id     │
└─────────────┘   └────────────┬───────────────┘
                               │ в лимите?
                      ┌────────┴────────┐
                 ┌────▶  нет (ок)      да (429) ──▶ запись rejected в БД
                 │
                 ▼
┌─────────────────────────────────┐
│ Обработчик:                     │
│  • ключ задан   → LLM (ProxyAPI)│
│  • ключа нет    → база знаний   │
│    (examples/knowledge_base.json│
│     точное совпадение → ключи)  │
└───────────────┬─────────────────┘
                ▼
      Нормализация ответа (category/confidence/escalate, при `low` → escalate=true)
                ▼
   ┌──────────────────────────────┐
   │ SQLite: tickets + channels   │  ── аудит истории
   │ Логи: app.log / error.log    │
   │       / requests.log         │
   └──────────────────────────────┘
```

Слои проекта (`app/`): `api/routes.py` (эндпоинты), `core/triage_service.py` (оркестрация),
`core/llm.py` (клиент LLM + разбор JSON), `core/knowledge_base.py` (демо-режим без ключа),
`core/rate_limiter.py`, `db/database.py` (SQLite), `config.py` (настройки из env).

## 4. Контракт программного интерфейса (пример вход / выход)

**Запрос `POST /triage`:**

```json
{
  "text": "Мне дважды списали деньги за подписку, верните, пожалуйста, один платёж.",
  "channel": "email",
  "client_id": "client-001"
}
```

**Ответ (200):**

```json
{
  "category": "billing",
  "draft_reply": "Здравствуйте! Проверим ваш платёж по подписке...",
  "confidence": "medium",
  "escalate": false
}
```

**Коды ошибок:** `422` — невалидный вход (список полей), `429` — превышен лимит для `client_id`,
`500` — сбой записи в БД / непредвиденная ошибка (без деталей стека).

**Сбой LLM — не HTTP-ошибка:** возвращается `200` с `escalate=true`, `confidence=low` и
шаблонным `draft_reply` «Ваш запрос передан оператору поддержки…» (сценарий «если всё сломалось»).

## 5. Как устроен журнал обработки (что хранится в БД)

SQLite-файл `data/tickets.db` создаётся автоматически при первом запуске и переиспользуется.
Таблицы:

- **`tickets`** — история обращений:
  `id, created_at, client_id, channel, text, category, confidence, escalate, draft_reply, error`
  (поле `error` фиксирует причину, если обработка не удалась / превышен лимит);
- **`channels`** — справочник каналов (`email`, `form`, `chat`).

Целостность на уровне БД: `channel` — внешний ключ на `channels`, `NOT NULL` и `CHECK` на
допустимые значения, индексы по `created_at` и `client_id`.

Параллельно ведётся журнал в файлах: `logs/app.log` (события), `logs/error.log` (ошибки),
`logs/requests.log` (аудит HTTP-запросов).

## 6. Надёжность (эскалация, лимиты, логирование)

- **Валидация входа** — Pydantic-схема + отсечение пробелов, ошибки возвращаются списком полей;
- **Секреты** — `LLM_API_KEY` читается только из `.env`/окружения; `.env` в `.gitignore`;
- **Лимитирование** — скользящее окно в памяти, `RATE_LIMIT_PER_MINUTE` (5) на `client_id`;
  превышение фиксируется в БД (`error='rate_limit_exceeded'`) и сопровождается `429`;
- **Эскалация** — правило: `confidence=low` или флаг модели ⟹ `escalate=true`;
- **Фолбэк «если всё сломалось»** — при ошибке LLM / таймауте / невалидном JSON сервис возвращает
  `200` с `escalate=true` и шаблонным ответом, причина пишется в БД и `error.log` — 500-страница не генерируется;
- **Демо-режим без ключа** — при отсутствии `LLM_API_KEY` ответы подбираются из `examples/knowledge_base.json`
  (точное совпадение → ключевые слова → общий шаблон), что позволяет прогнать демо без сети и без ключа;
- **Промпт + `temperature=0.2`** — модель обязана работать строго по тексту, не выдумывать факты,
  при нехватке данных ставить `low` + эскалацию;
- **Проверки** — 47 юнит/интеграционных тестов (pytest) и смоук-тест сервиса (`python scripts/run_checks.py`)
  зелёные (последний прогон: 47 passed, 15/15 смоук).

## 7. Развёртывание / демонстрация

**Выбран путь B (запасной): публичная демонстрация без размещения на платном сервере.**

- Сервис запускается локально (`uvicorn app.main:app`, пошагово — `RUN_LOCALLY.md`);
- демо-видео «запрос → ответ → запись в БД» (2–3 минуты) + скриншоты health, ответа API,
  содержимого SQLite-файла и логов — приложены отдельно;
- README содержит шаги локального запуска, пример запроса, информацию о БД и логах.

**Подготовлен также путь A (на будущее, без платного хостинга полностью готов к нему):**
`Dockerfile` + `docker-compose.yml` (сервис + Caddy с автоматическим HTTPS) и инструкция для
бесплатного PaaS (Render/Railway): стартовая команда `uvicorn app.main:app`, секреты в env,
постоянные тома для SQLite и логов.

## 9. Что улучшить в v2

1. **RAG / полноценная база знаний** — подключение документов (инструкции, тарифы, FAQ)
   с поиском по эмбеддингам вместо демонстрационного JSON-подбора;
2. **Мониторинг** — метрики (latency, ошибки LLM, количество эскалаций), алерты,
   health с проверкой доступности LLM;
3. **Админка** — интерфейс менеджера для просмотра очереди, редактирования черновиков
   и доработки тикетов;
4. **Адаптеры каналов** — реальные интеграции email/формы/чата вместо метки `channel`;
5. **Устойчивость** — PostgreSQL вместо SQLite, ретраи/таймауты LLM с fallback-провайдером,
   авторизация запросов (API-ключ) и rate-limit на IP в дополнение к client_id;
6. **Интеграционные тесты со «живой» моделью** и векторные метрики качества классификации.
