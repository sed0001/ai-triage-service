# AI Triage Service

ИИ-сервис первичной обработки обращений поддержки.
Учебный проект **VPk04.1** (Карьерный блок 2, кейс-лаборатория «ИИ-сервис для обработки обращений»).

## О чём проект

**Проблема.** Менеджеры поддержки тратят время на первичную сортировку обращений и типовые
ответы: «версите деньги», «не открывается кабинет», «как сменить тариф» — однотипные запросы
занимают до 80% входящих. Из-за этого падает скорость реакции и качество обслуживания.

**Решение.** Сервис принимает текст обращения, классифицирует его по типу
(`billing | support | complaint | other`), пишет черновик ответа для менеджера, оценивает
уверенность и решает, отвечать автоматически или передать сложный/неоднозначный случай человеку.
Каждый запрос и результат сохраняются в базу (аудит), всё логируется, а ключевые сценарии
(незаполненные поля, превышение лимита, сбой языковой модели) отрабатывают без падения сервиса.

**Результат для бизнеса:** быстрее реакция, ниже нагрузка на менеджеров, прозрачная история
обращений.

## Возможности

- **POST /triage** — классификация + черновик ответа + уверенность + эскалация;
- **GET /health** — проверка состояния сервиса и базы данных;
- **SQLite-аудит** — таблица `tickets` хранит вход, результат и текст ошибки по каждому запросу;
- **Валидация входа** — `text` 1…2000 символов, `channel` только `email|form|chat`, обязательный `client_id`;
- **Лимитирование** — скользящее окно N запросов/мин на `client_id` (по умолчанию 5);
- **Сценарий «если всё сломалось»** — при ошибке LLM сервис возвращает `escalate: true`
  и шаблонный ответ «передано оператору» вместо 500-й страницы;
- **Демо-режим без ключа** — без `LLM_API_KEY` ответы подбираются из локальной базы знаний
  `examples/knowledge_base.json` (точное совпадение → ключевые слова → общий шаблон);
- **Безопасность** — ключ LLM только в `.env`, файл в `.gitignore`;
- **Логирование** — `logs/app.log`, `logs/error.log`, `logs/requests.log`;
- **Понятные ошибки** — 422/429/500 с человекочитаемыми сообщениями.

## Быстрый старт (за 5–10 минут)

Требуется Python 3.10+.

> Полная пошаговая инструкция со скриншотами и примерами — в **[`RUN_LOCALLY.md`](RUN_LOCALLY.md)**.

```bash
# 1. Скопировать пример настроек и вписать API-ключ
cp .env.example .env
# Windows PowerShell: Copy-Item .env.example .env

# 2. Создать и активировать виртуальное окружение
python -m venv .venv
# Windows: .venv\Scripts\activate      |  macOS/Linux: source .venv/bin/activate

# 3. Установить зависимости
pip install -r requirements.txt

# 4. Вписать в .env API-ключ ProxyAPI
#    LLM_API_KEY=sk-...   (создать: https://console.proxyapi.ru/keys)

# 5. Запустить сервис (обязательно из корня проекта)
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Готово. Проверьте:

- Health: `http://127.0.0.1:8000/health`
- Интерактивная документация: `http://127.0.0.1:8000/docs`
- Пример обращения:

```bash
curl -X POST http://127.0.0.1:8000/triage \
  -H "Content-Type: application/json" \
  -d '{"text": "Мне дважды списали деньги за подписку.", "channel": "email", "client_id": "client-001"}'
```

> **Без ключа `LLM_API_KEY`** сервис работает в демо-режиме базы знаний:
> тексты из `examples/test_data.md` вернут свои ответы из `examples/knowledge_base.json`
> один в один, а прочий текст — честный шаблон «передано оператору» с `escalate: true`.
> Это удобно, чтобы прогнать демо вообще без ключа и без сети.

## Конфигурация (.env)

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `LLM_API_KEY` | — | API-ключ ProxyAPI (обязателен для реальной обработки) |
| `LLM_BASE_URL` | `https://api.proxyapi.ru/openai/v1` | OpenAI-совместимый эндпоинт LLM |
| `LLM_MODEL` | `gpt-4o-mini` | Модель для триажа |
| `LLM_TEMPERATURE` | `0.2` | Низкая температура = меньше «фантазии» |
| `LLM_TIMEOUT_SECONDS` | `60` | Таймаут вызова LLM |
| `RATE_LIMIT_PER_MINUTE` | `5` | Максимум запросов в минуту на `client_id` |
| `DB_PATH` | `data/tickets.db` | Путь к SQLite-файлу |
| `LOG_DIR` | `logs` | Папка для логов |
| `KNOWLEDGE_BASE_PATH` | `examples/knowledge_base.json` | База знаний демо-режима (используется, если `LLM_API_KEY` пуст) |
| `APP_HOST` / `APP_PORT` | `0.0.0.0` / `8000` | Адрес запуска (используется в логах) |

## Контракт API

### POST `/triage`

Вход (JSON):

```json
{
  "text": "Мне дважды списали деньги за подписку, верните платеж.",
  "channel": "email",
  "client_id": "client-001"
}
```

| Поле | Тип | Ограничения |
|---|---|---|
| `text` | string | 1…2000 символов, обязательно |
| `channel` | string | `email` \| `form` \| `chat` |
| `client_id` | string | 1…128 символов, обязательно |

Выход (JSON):

```json
{
  "category": "billing",
  "draft_reply": "Здравствуйте! Проверим ваш платёж по подписке...",
  "confidence": "medium",
  "escalate": true
}
```

| Поле | Значения | Комментарий |
|---|---|---|
| `category` | `billing` \| `support` \| `complaint` \| `other` | Тип обращения |
| `draft_reply` | строка, 1–6 предложений | Черновик ответа менеджеру (на русском) |
| `confidence` | `high` \| `medium` \| `low` | Уверенность модели |
| `escalate` | `true` / `false` | `true` — передать человеку |

Эскалация ставится принудительно, если `confidence: low` или при сбое/невалидном ответе LLM.

### Коды ошибок

| Код | Ситуация | Сообщение |
|---|---|---|
| 422 | Невалидный вход | Список полей с причинами |
| 429 | Превышен лимит `RATE_LIMIT_PER_MINUTE` для `client_id` | «Слишком много запросов…» |
| 500 | Ошибка записи в БД / непредвиденная ошибка | Понятное сообщение без стека |

## Тестовые данные

Файл `examples/test_data.md` содержит **6 готовых текстовых обращений** с ожидаемыми
категориями — их можно отправлять в `POST /triage` как есть (в поле `text`).

## База знаний (демо без ключа LLM)

Если `LLM_API_KEY` не задан, сервис не обращается к модели, а подбирает готовый ответ
из `examples/knowledge_base.json`:

1. **точное совпадение** текста обращения с `match_text`;
2. иначе — **первое совпадение по ключевым словам** (`keywords`);
3. иначе — общий шаблон «передано оператору» с `escalate: true`.

Каждая запись задаёт `category`, `confidence`, `escalate` и `draft_reply` — их можно
править без изменения кода. Так тестовые обращения из `test_data.md` воспроизводятся
один в один даже без доступа к API.

## Логи и база данных

### Где смотреть

- **Логи** — папка `logs/` (создаётся при первом запуске):
  - `app.log` — все события сервиса;
  - `error.log` — только ошибки (сбои LLM, валидация, недоступность БД);
  - `requests.log` — аудит HTTP-запросов (метод, путь, статус, длительность).
- **База** — файл `data/tickets.db`, таблицы:
  - `tickets` — обращения: `id, created_at, client_id, channel, text, category,
    confidence, escalate, draft_reply, error`;
  - `channels` — справочник каналов (`email`, `form`, `chat`).

Целостность на уровне БД: `channel` ссылается на справочник `channels` (внешний ключ),
обязательные поля и категория/уверенность/`escalate` ограничены `NOT NULL` и `CHECK`;
есть индексы по `created_at` и `client_id`.

Файл БД **создаётся автоматически при первом запуске**; при повторных запусках
используется существующий файл — данные не теряются.

### Пример запроса к базе

```bash
sqlite3 data/tickets.db "SELECT id, client_id, category, confidence, escalate, error FROM tickets ORDER BY id DESC LIMIT 10;"
```

## Надёжность и безопасность

1. **Валидация входа** — Pydantic-схема + отсечение пробелов; ошибки возвращаются списком полей.
2. **Секреты** — ключ LLM читается только из окружения/`.env`; `.env` в `.gitignore`.
3. **Лимитирование** — скользящее окно в памяти, `RATE_LIMIT_PER_MINUTE` на `client_id`.
4. **Фолбэк для LLM** — если модель недоступна, вернула таймаут или невалидный JSON, сервис
   возвращает `200` с `escalate: true`, `confidence: low` и шаблонным ответом;
   причина записывается в БД и `error.log`. Без ключа LLM аналогично ведёт себя
   **демо-режим базы знаний**: совпадение из JSON → свой ответ, иначе — тот же шаблон.
5. **Промпт** — модель обязана работать строго по тексту обращения, не выдумывать факты,
   при нехватке данных ставить `low` + эскалация; `temperature=0.2`.

## Развёртывание

Проект готов к публикации; ниже два пути — на собственном VPS (Docker Compose + Caddy)
или на бесплатном PaaS. В обоих случаях нужен **реальный домен или DNS-запись** и
переменная `LLM_API_KEY` в окружении (на сервере ключ хранится как секрет, не в репозитории).

### Путь A — VPS + Docker Compose + Caddy (HTTPS)

Подходит для Ubuntu/Debian-сервера (можно арендовать на любой VPS-провайдере).
Caddy берёт на себя HTTPS: сам выпускает сертификат Let's Encrypt и проксирует трафик.

1. Установить на сервер **Docker Engine** и **Docker Compose v2** (официальная инструкция
   docker.com: «Install Docker Engine»). Секретов в контейнере не будет, только тома.
2. Скопировать проект на сервер (например, `git clone …`).
3. Создать `.env` из `.env.example` и вписать:
   ```
   LLM_API_KEY=sk-...
   CADDY_DOMAIN=triage.example.com   # ваш домен, указывает на IP сервера (запись A)
   ```
4. Открыть на сервере порты `80` и `443` (в панели провайдера и в файрволе).
5. Запустить (при первом запуске собирается образ, это займёт минуту-две):
   ```bash
   docker compose up -d
   ```
6. Проверить:
   - `https://triage.example.com/health` → `{"status": "ok", ...}`;
   - `POST https://triage.example.com/triage` через Postman/curl.
7. Обновление: `git pull` → `docker compose up -d --build`.

Что делают файлы: `docker-compose.yml` — сервис `triage` (FastAPI + SQLite) и `caddy`
(обратный прокси); `Caddyfile` — «все запросы домена → `triage:8000`». SQLite-файл и логи
лежат в Docker-томах и переживают перезапуски (`docker compose down` их не стирает).

### Путь B — бесплатный PaaS (Render / Railway / Fly.io)

Сервис — обычное FastAPI-приложение, поэтому подходит для PaaS без VPS:
1. Импортировать репозиторий в панель платформы (Render: «New Web Service» → connect repo).
2. Стартовая команда: `uvicorn app.main:app --host 0.0.0.0 --port 8000`.
3. Переменные среды: скопировать строки из `.env.example`; `LLM_API_KEY` добавить в раздел
   secrets/env (не в код). `DATA_DIR`/`LOG_DIR` задать в `/tmp` (у бесплатных PaaS нет
   постоянного диска, файлы живут только пока запущен инстанс).
4. БД и логи PaaS хранит в памяти процесса — для MVP критерия «запись в БД и логи»
   достаточно продемонстрировать на **локальном запуске** (см. `RUN_LOCALLY.md`).
5. После деплоя платформа выдаст HTTPS-адрес вида `https://<имя>.onrender.com` — им и
   проверять `POST /triage`.

### Локальная проверка (запасной путь для сдачи)

Локальный запуск — пошагово, со скриншотами/запуском curl, описан в **`RUN_LOCALLY.md`**:
создание `.env`, venv, uvicorn, проверка health, `examples/test_data.md`, чтение БД и логов.
Этого достаточно для демонстрации «запрос → ответ → запись в БД».

## Ограничения и планы v2

- Лимитер живёт в памяти одного процесса — при горизонтальном масштабировании понадобится
  общее хранилище (Redis).
- Черновик ответа не нормируется по числу предложений (зависит от модели).
- Категорий ровно 4, без RAG/базы знаний — по условиям практики. В v2: подключение базы
  знаний, мониторинг метрик, админка для просмотра тикетов, улучшенная эскалация.

## Устранение неполадок

| Симптом | Причина / решение |
|---|---|
| Любой запрос возвращает «передано оператору» | В демо-режиме не нашлось совпадения в базе знаний (проверьте `examples/knowledge_base.json`), либо задан `LLM_API_KEY`, но модель недоступна — смотрите `logs/error.log` |
| Ошибка при импорте модулей | Запускайте `uvicorn` из корня проекта (папка с файлом `app/`), не из `app/` |
| Порт занят | Смените `--port` или остановите процесс на порту |
| `LLM_API_KEY` не подхватывается | Проверьте, что файл `.env` в корне проекта и переменной нет в системном окружении с пустым значением |
| Сбой LLM со статусом 4xx/5xx | Проверьте ключ и баланс в личном кабинете ProxyAPI |
